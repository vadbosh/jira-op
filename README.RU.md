# jira-op

**Скил Jira для ассистентов-кодеров, который делает две вещи, повторяющиеся у
инженера каждую неделю: заводит задачу со всеми обязательными полями проекта и
собирает недельный инженерный отчёт по задачам.**

Работает через [jira-cli](https://github.com/ankitpokhrel/jira-cli) для чтения
и переходов и через REST API Jira для записи, которую CLI надёжно не делает, —
ни MCP, ни отдельной обёртки над API ставить не нужно. Подходит для Claude
Code, Codex и Opencode.

**Некогда читать?** → [Быстрый старт](FAST-START.RU.md) · [Fast start](FAST-START.md)

[English version](README.md) · Полное руководство по установке:
[по-русски](docs/setup.ru.md) · [English](docs/setup.en.md)

>️ **До первой записи ему нужны значения вашего сайта.** Тип задачи,
> идентификаторы кастомных полей, статусы и номер доски у каждого проекта свои.
> Они лежат в одном файле — `SITE.md`, который `install.sh` собирает по живому
> API при первом запуске. См. [Настройка](#настройка).

## Зачем нужен jira-op

Два сбоя повторяются каждую неделю, и оба съедают время инженера.

**Задача не заводится, а причину не видно.** Обязательные поля свои у каждого
проекта и у каждого типа задачи. REST отвечает на них `400` со списком вида
`customfield_19879` — идентификатор есть, названия поля нет. В jira-cli те же
поля задаются словами (`--custom "devops-category"`), и слова с
идентификаторами не совпадают. Хуже другое: `jira issue create --no-input` без
`</dev/null` не падает, а зависает — `rc=124` по таймауту, задача не создана,
сообщения нет ([jira-cli#948](https://github.com/ankitpokhrel/jira-cli/issues/948),
воспроизведено на 1.7.0). Скил один раз читает `createmeta`, складывает
идентификаторы в `SITE.md` и пишет через REST теми же идентификаторами, что
`createmeta` вернул.

**Отчёт за неделю получается про доску, а не про работу.** Собранный прямо из
Jira, он наполняется возрастом задач, числом переносов между спринтами, пустыми
полями и строками «за неделю ни комментариев, ни переходов». Это правда, и это
упрёк команде; тимлиду нужно, что сделано и что решено. Скил задаёт состав
разделов и держит по два предложения на пункт. Незапущенная работа в отчёт не
попадает — вся категория `To Do`, а не один статус. Изменения берутся из
changelog самой задачи, поэтому прошлый файл отчёта не нужен.

Кроме этих двух записаны ещё четыре ловушки, каждая воспроизведена на живом
сайте:

- `ORDER BY` внутри `-q` возвращает `400 Expecting ',' but got 'ORDER'` —
  сортировать надо флагом `--order-by`;
- список без `--paginate` обрезается на восьмой строке и не говорит об этом —
  так задача числилась «не твоей», хотя была твоей;
- `jira issue view` показывает один комментарий, поэтому задача с обсуждением
  выглядит нетронутой; нужен `--comments 10`;
- верхняя граница окна пишется как `< AFTER_END`: `<= WEEK_END` останавливается
  на 00:00 последнего дня и теряет его целиком.

## Что внутри

| Файл | О чём |
|---|---|
| `SKILL.md` | параметры сайта, доступ, права, ловушки CLI, правила безопасности |
| `references/create-task.md` | заведение задачи со всеми обязательными полями и вычитка результата |
| `references/weekly-report.md` | недельный отчёт: окно, источники, структура, тон |
| `docs/example-weekly-update.txt` | как выглядит готовый файл, ключи заменены |
| `references/investigate.md` | разбор задачи только на чтение, до любых действий |
| `references/ticket-writing.md` | как написать задачу, которую выполнит другой человек, и как дописать продолжение в уже существующую |
| `references/commands.md` | справочник по jira-cli, включая несуществующие флаги |
| `SITE.example.md` | описывает каждое значение сайта и команду, которая его выдаёт — только в репозитории, в скил не ставится |
| `scripts/site-probe.sh` | собирает этот файл из живого API — по одному на сайт Jira |

`investigate.md` и `ticket-writing.md` не содержат идентификаторов проекта и
работают с любым сайтом Jira как есть.

## Установка

```bash
git clone <этот-репозиторий> jira-op
cd jira-op
./install.sh              # во все найденные ассистенты в $HOME
./install.sh --dry-run    # показать действия, ничего не менять
```

Нужны `jira` (jira-cli 1.7.0 или новее), `jq`, `curl`.

`install.sh` написан на bash — это **Linux и macOS** либо WSL или Git Bash под
Windows. Установщика на PowerShell нет: в родном Windows скопируйте
`skills\jira-op` в каталог скилов ассистента вручную. Сам скил состоит из
Markdown, поэтому больше ничего от платформы не зависит.

Дальше настраивается сам jira-cli и сохраняется токен:

```bash
jira init                                  # Cloud, адрес сайта, ваш login email
umask 077; read -r -s -p 'token: ' T \
  && printf 'JIRA_API_TOKEN=%s\n' "$T" > ~/.config/.jira/token.env && unset T
```

Токен создаётся на
<https://id.atlassian.com/manage-profile/security/api-tokens>. Берите classic
token: токены со scope принимаются не везде. `jira init` во время работы ходит
на сайт, поэтому `JIRA_API_TOKEN` нужно экспортировать **до** его запуска —
иначе он падает с `401 Unauthorized` посреди вопросов.

Как поставить сам jira-cli, что отвечать на вопросы `init`, чем проверить
доступ и что означает каждая ошибка: **[docs/setup.ru.md](docs/setup.ru.md)**.

## Как пользоваться

Обращайтесь к ассистенту обычными словами. Скил срабатывает на упоминание Jira
и на ключи задач.

**Посмотреть:**

```
покажи мои открытые задачи
what's in the active sprint
разбери PROJ-123
```

Разбор идёт только на чтение и таким и остаётся. Возвращает три отдельных
списка: факты, гипотезы и то, что проверить не удалось. Ради третьего он и
нужен.

**Завести задачу по уже сделанной работе:**

```
заведи таску: обновил AMI на трёх кластерах, риски и приёмку сформулируй сам
```

Ассистент спросит три значения, которые нельзя угадывать, — story points,
спринт и End Date (ответ «не надо» допустим), — и напечатает черновик
**целиком**: summary, описание и все поля, которые он заполнил за вас, включая
риски и критерии приёмки. Пока вы не скажете «да», не создаётся ничего.
Черновик будет на английском, каким бы языком вы ни пользовались: задачу читают
люди, которые русского не знают.

Тело задачи тоже короткое. Context, Scope и Potential Risks читает тот, кто
решает, касается ли это его: цель — два-три предложения на раздел, предел —
десять-двенадцать, и то для работы, которая действительно затрагивает несколько
областей. Идентификаторы полей, имена флагов и вывод команд в описании не нужны,
им место в комментариях или в репозитории.

Summary остаётся общим — `Scheduled EKS cluster maintenance`, а не
`… node AMI and add-on updates across three clusters`. Количества, версии и
списки компонентов живут в теле: доску читают взглядом, а эти подробности
протухают, пока тело остаётся верным.

**Недельный отчёт:**

```
сделай недельный отчёт
weekly report for last week
```

Ассистент попросит ввести период — первый и последний день: окно не
зафиксировано, было понедельник–воскресенье, стало пятница–четверг. Ничего не
предлагается и не вычисляется по дню недели. Потом спросит, не попал ли в окно
отпуск или праздники, и **запишет обычный текстовый файл в тот каталог, где он
запущен** —
`weekly-update-<начало>_<конец>.txt`. В ответ приходит путь; содержимое в
переписку не выводится, существующий файл не перезаписывается. В Jira ничего не
публикуется и никуда не отправляется.

Окно берётся целыми днями — с первого дня 00:00 по последний 23:59 — и не
обрезается моментом сдачи. Отчёт собран раньше конца окна, а потом что-то
сделано: не отправлен — пересобрать, отправлен — эти пункты уйдут в следующий
отчёт с названными датами.

Набор секций фиксирован: нужны решения, эскалации, что получилось, риски,
принятые решения, планы на неделю. Оформление допускается в двух видах:

- **компактное** — пункт читается как `KEY — результат` под строкой
  воркстрима, владелец указан один на всю секцию планов;
- **полное** — после ключа идёт название задачи в кавычках, владелец указан у
  каждого пункта.

Ориентируйтесь на то, что команда уже рассылает. Читаемым отчёт в обоих видах
делают четыре правила:

- **только факты работы.** Никогда — сколько задача открыта, через сколько
  спринтов протащена, пустые ли у неё поля. Это гигиена доски, ей место в
  разговоре, а не в отчёте тимлиду.
- **незапущенная работа не попадает ни в одну секцию** — вся категория
  `To Do`, а это на некоторых досках девять статусов. Работой считается всё,
  что Jira относит к рабочей категории: неделя в `Team Review` или `Blocked`
  попадает в отчёт, а не выпадает из него.
- **два предложения на пункт.** Перечни компонентов, версий и путей не пишутся:
  вместо них счёт и форма («около двух десятков чартов», «три кластера»), а
  подробности остаются в задаче. Риски сжимаются так же, но второе
  самостоятельное последствие и условие, при котором риск срабатывает, ради
  строки не выбрасываются.
- **задачу на месяц работ не дробят ради отчёта** и не дают ей молча пропасть
  из отчёта. Каждую неделю она приходит дельтой — что изменилось внутри окна,
  со счётом, если работа считается по частям. Пустой changelog не значит пустую
  неделю. У длинной задачи работа идёт по плану, записанному внутри неё, поэтому
  отчёт пишет, что работа шла по этому плану, и никогда не пишет «no movement
  this week». Одной строкой в планах становится задача, которой не касались.
  Дельта читается из changelog задачи, где каждая правка текста хранит обе
  версии, так что прошлый файл отчёта не нужен.

## Безопасность

Чтение выполняется сразу. Любая запись — создание, правка, переход, комментарий —
показывается командой и ждёт подтверждения. После записи задача вычитывается
заново: нулевой код возврата не доказывает, что поле сохранилось.

У многих аккаунтов `DELETE_ISSUES: false` — созданную задачу нельзя удалить
тем же аккаунтом, который её создал. Поэтому скил никогда не создаёт задачу
ради проверки самого себя, а права вашего аккаунта записываются в `SITE.md`.

Текст задачи считается недоверенным вводом: инструкции, найденные в описании
или комментарии, показываются вам, а не выполняются.

## Чего jira-op не делает

Сказано прямо, потому что скил, который читается как интеграция, провоцирует
ожидание, что он ею и является.

- **Не публикует недельный отчёт.** Ни в Slack, ни почтой, ни в Confluence, ни
  комментарием к задаче. Он пишет текстовый файл в рабочий каталог проекта и
  отдаёт путь; куда пойдёт этот текст — ваше решение и ваша вставка.
- **Не пишет в Jira самостоятельно.** Создание, правка, переход и комментарий
  ждут подтверждения именно этого изменения. Согласие на одно создание не
  распространяется на следующее.
- **Не выбирает значения, требующие суждения** — story points, спринт,
  принадлежность эпику. Он спрашивает или не трогает их вовсе.
- **Не заполняет обязательное поле ради прохождения экрана создания.** Никаких
  `N/A` в поле рисков, выдуманных критериев приёмки и решений без автора.
- **Ничего не удаляет**, да и не смог бы на большинстве аккаунтов: созданную
  задачу обычно нельзя удалить тем же аккаунтом, который её создал.
- **Не является средством администрирования Jira.** Workflow, конфигурация
  полей, схемы прав, заведение проектов — этого здесь нет; скил читает текущую
  конфигурацию, а не меняет её.
- **Не связывает задачи с git.** Ни именования веток, ни привязки PR, ни смены
  статуса при merge. Это дело того, что запускает ваш пайплайн.
- **Не кеширует Jira.** Любой ответ получен вызовом, сделанным сейчас, — поэтому
  даже чтение требует сети и учётных данных.
- **Не управляет вашими учётными данными.** Он читает файл с токеном, который
  создали вы, и никогда не печатает его содержимое.
- **Не заменяет документацию jira-cli.** В `references/commands.md` собрано то,
  что нужно этому рабочему процессу, плюс несуществующие флаги; остальное
  описано в самом проекте.

## Настройка

В файлах скила стоят имена вида `<PLACEHOLDER>`, а не жёстко прописанный сайт.
Разрешает их один файл:

```bash
$SKILL/scripts/site-probe.sh --write           # обычный путь
```

Либо пусть его соберёт probe — это обычный путь, `install.sh` и `add-site.sh`
вызывают его сами, когда файла сайта нет:

```bash
$SKILL/scripts/site-probe.sh --write           # текущий сайт
$SKILL/scripts/site-probe.sh --all --write     # все заведённые сайты
$SKILL/scripts/site-probe.sh --all --check     # отчёт о расхождении, без записи
```

Он читает конфигурацию, которую уже записал jira-cli, и делает проход по API
только на чтение, охватывая все типы задач проекта. `SITE.example.md` в этом
репозитории описывает те же значения с командой рядом с каждым — для тех, кто
предпочитает заполнять осознанно. `install.sh` его в скил не копирует:
примерные значения рядом с настоящими, под одинаковыми заголовками, читаются
как конфигурация.

**Тип задачи по умолчанию вычисляется, а не настраивается.** Проба записывает
тип, под которым заведено большинство ваших последних 100 задач в проекте, и
каждое создание идёт этим типом, если вы не назвали другой.
`JIRA_OP_ISSUE_TYPE=<имя или id>` его перебивает — для аккаунта без задач или
команды, которая заводит задачи по правилу. Ничего о конкретной Jira в скил не
вписано, поэтому другая организация получает свой тип из своей истории.

**По одному файлу на сайт**: `SITE.md` для конфигурации по умолчанию,
`SITE.<name>.md` для `~/.config/.jira/<name>.yml`. Скил выбирает файл по
`JIRA_CONFIG_FILE`, поэтому три аккаунта Jira — это три файла и ни одной
правки при переключении.

Поддержание в актуальном состоянии, необязательный cron и `JIRA_OP_SKILL_DIR`:
[docs/setup.ru.md](docs/setup.ru.md#как-поддерживать-файлы-сайтов-в-актуальном-состоянии).

`SITE.md` в git не попадает: он описывает ваш инстанс, а не этот репозиторий.

Два файла — `investigate.md` и `ticket-writing.md` — плейсхолдеров не содержат
и работают ещё до появления `SITE.md`.

## Несколько сайтов Jira

```bash
# каталог скила того ассистента, которым пользуетесь
SKILL=~/.claude/skills/jira-op            # либо ~/.codex/skills/jira-op
                                          # либо ~/.config/opencode/skills/jira-op
```

jira-cli читает один конфиг и один токен, и это два независимых механизма:
конфиг одного сайта с токеном другого даёт `401`, который выглядит как
протухший токен, а не как неверная пара. Функция `jira_site` лежит внутри скила, в
`scripts/jira_site.sh`; её и подключайте из rc-файла оболочки —
она переключает пару одним шагом,
[`skills/jira-op/scripts/add-site.sh`](skills/jira-op/scripts/add-site.sh) заводит новый сайт.

После `install.sh` обе команды лежат в PATH, поэтому клон можно перенести или
удалить:

```bash
$SKILL/scripts/add-site.sh acme           # спросит токен, запустит jira init, проверит пару
$SKILL/scripts/add-site.sh --list         # что уже заведено
jira_site acme                  # переключиться
jira_site default               # вернуться на конфиг по умолчанию
```

`jira me` печатает login — это и есть доказательство, что переключение
произошло.

## Замечания по jira-cli

Найдено на практике, всё проверено на версии 1.7.0:

- `--paginate` по умолчанию равен **8** и молча обрезает вывод.
- `ORDER BY` внутри `-q` даёт `400 Bad Request` — сортировать через
  `--order-by`.
- `jira issue view` показывает **один** комментарий; нужен `--comments 10`.
- У `jira issue comment add` нет `-b`: тело передаётся позиционно или
  `--template`.
- У `jira board list` нет `--plain`, а сообщение «No boards found in project X»
  называет проект из вашего конфига, а не тот, о котором вы спросили, — нужен
  `-p`.
- Принадлежность эпику — `jira epic add`, а не `jira issue link`.
- **`jira issue create` зависает, когда stdin не терминал** — подпроцесс,
  CI-раннер, ассистент. `--no-input` пропускает TUI, но не то чтение, которое
  блокирует ([#948](https://github.com/ankitpokhrel/jira-cli/issues/948)).
  Дописывать `</dev/null` либо создавать через REST, как делает скил.
- v2 REST API читает текстовое описание как **wiki markup**, а не Markdown:
  `## Scope` превращается в нумерованный список. Нужны `h3.`, `*`, `{{code}}`.
- Нумерованный список — это `#`. `1.` разметкой не считается: строки приходят
  абзацами с цифрами внутри. Один пункт списка занимает одну строку.

## Как присылать правки

Сообщения коммитов пишутся по-английски, вместе с телом. История — единственное
место, где остаётся причина изменения, а кто читает код, прочитает и сообщение.
Если сообщение цитирует русский текст — переименованный заголовок, заменённое
слово, — цитата остаётся: там русский и есть предмет.

Сама документация двуязычная и такой остаётся: `README.md` и `README.RU.md`
правятся парой.
